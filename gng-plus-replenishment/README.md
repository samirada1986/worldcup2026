# GNG+ — اتوماسیون سفارش‌دهی کالا (نمونه اولیه)

نمونه اولیه اجراپذیر ماژول **سفارش‌دهی کالا / درخواست خرید خودکار** برای ERP گنگ‌پلاس.

فرآیند دستی فعلی:

```
پارامترهای سفارش‌دهی کالا → بررسی موجودی → ورود کاربر به فرم → جستجو
→ مشاهده کالاهای نیازمند سفارش → تعیین مقدار درخواست → ارسال درخواست خرید
```

فرآیند هدف که در این نمونه پیاده‌سازی شده است:

```
Trigger → خواندن پارامترها → خواندن موجودی → محاسبه موجودی موثر
→ محاسبه مصرف → ارزیابی قواعد → تولید پیشنهاد → بررسی درخواست‌های باز
→ ایجاد پیش‌نویس درخواست خرید → بازبینی کاربر → ارسال به گردش‌کار → ثبت تاریخچه
```

در نسخه ۱ **اتوماسیون خودگردان کامل پیاده‌سازی نشده است**. مدل کار
Human-in-the-loop است: اتوماسیون فقط محاسبه می‌کند، پیشنهاد می‌دهد و
**پیش‌نویس** می‌سازد؛ تصمیم و ارسال به گردش‌کار با کاربر است.

## ۱. معماری

```
                    ┌──────────────────────────────────────┐
   مرورگر  ───────► │  Angular 18 (standalone, DevExtreme) │
                    │  فقط تعامل و نمایش — بدون محاسبه      │
                    └───────────────┬──────────────────────┘
                                    │  REST/JSON  (proxy: /api → :5220)
                    ┌───────────────▼──────────────────────┐
                    │  ASP.NET Core 8 — Controllers        │
                    ├──────────────────────────────────────┤
                    │  Application — Services + Calculator │  ◄── تمام منطق کسب‌وکار
                    ├──────────────────────────────────────┤
                    │  Infrastructure — EF Core Repos      │
                    ├──────────────────────────────────────┤
                    │  Domain — Entities + Enums           │
                    └───────────────┬──────────────────────┘
                                    │
                          SQLite (یا InMemory)
```

**اصل حاکم:** هیچ محاسبه یا تصمیم کسب‌وکاری در فرانت‌اند انجام نمی‌شود.
موجودی موثر، میانگین مصرف، مقدار پیشنهادی و وضعیت هر ردیف، همگی از بک‌اند
می‌آیند. فرانت‌اند فقط نمایش می‌دهد و ورودی می‌گیرد.

اتوماسیون از طریق API و سرویس‌ها کار می‌کند، نه شبیه‌سازی کلیک کاربر؛
این یک لایه اتوماسیون متصل به گردش‌کار است، نه ربات RPA دسکتاپی.

## ۳. اجرا

### پیش‌نیازها

| ابزار | نسخه |
|---|---|
| .NET SDK | 8.0 |
| Node.js | 20 یا بالاتر |

### بک‌اند

```bash
cd backend/GngPlus.Replenishment.Api
dotnet run --urls http://localhost:5220
```

- **Swagger / OpenAPI:** <http://localhost:5220/swagger>
- ریشه (`/`) به Swagger هدایت می‌شود.

### فرانت‌اند

```bash
cd frontend
npm install
npm start          # معادل: ng serve
```

- **آدرس برنامه:** <http://localhost:4200>
- درخواست‌های `/api` از طریق `proxy.conf.json` به `http://localhost:5220`
  هدایت می‌شوند، بنابراین در حالت توسعه نیازی به تنظیم CORS نیست.
  (CORS در بک‌اند نیز برای `localhost:4200` فعال است.)

### پایگاه داده

- به‌صورت پیش‌فرض **SQLite** در فایل `gngplus-replenishment.db` کنار پروژه API.
- در نخستین اجرا پایگاه داده ساخته و **داده نمونه بارگذاری می‌شود**.
- برای شروع از صفر، فایل `.db` را حذف کنید و دوباره اجرا کنید.
- برای اجرای کاملاً درون‌حافظه، مقدار `ConnectionStrings:Replenishment` را
  در `appsettings.json` خالی بگذارید (آزمون‌ها از همین حالت استفاده می‌کنند).

هیچ Migration دستی لازم نیست؛ طرح پایگاه داده با `EnsureCreated` ساخته می‌شود.

## ۵. قواعد کسب‌وکار

همگی در `Application/Services/ReplenishmentCalculator.cs`.

### موجودی موثر

```
موجودی موثر = موجودی فعلی + ورودی قطعی − موجودی رزرو شده − مقدار درخواست خرید باز
```

### میانگین مصرف روزانه

```
میانگین مصرف روزانه = مجموع مصرف در پنجره / تعداد روزهای پنجره
```

پنجره تحلیل: بازه «از تاریخ / تا تاریخ» فیلتر و در نبود آن،
«تعداد روز برای محاسبه میانگین مصرف» همان پارامتر (پیش‌فرض ۳۰ روز).

### قواعد سفارش‌دهی

| نحوه سفارش‌دهی | شرط فعال شدن | مقدار پیشنهادی خام |
|---|---|---|
| `REORDER_POINT` | موجودی موثر ≤ نقطه سفارش | سطح مطلوب − موجودی موثر (در نبود سطح مطلوب: حداکثر موجودی) |
| `MIN_MAX` | موجودی موثر < حداقل موجودی | حداکثر موجودی − موجودی موثر |
| `DESIRED_LEVEL` | موجودی موثر < سطح مطلوب | سطح مطلوب − موجودی موثر |
| `CONSUMPTION_BASED` | موجودی موثر < موجودی هدف | موجودی هدف − موجودی موثر |

برای روش مبتنی بر مصرف:

```
تقاضای پیش‌بینی‌شده = میانگین مصرف روزانه × زمان تقریبی تامین
موجودی هدف        = تقاضای پیش‌بینی‌شده + مقدار ذخیره
```

### نرمال‌سازی مقدار

به ترتیب اعمال می‌شود:

1. مقدار پیشنهادی ≤ ۰ → **پیشنهادی ایجاد نمی‌شود**.
2. کمتر از **مقدار حداقل سفارش** → به آن افزایش می‌یابد.
3. کمتر از **مقدار بهینه سفارش** → به آن افزایش می‌یابد.
4. **اندازه انباشته سفارش** → گرد کردن **رو به بالا** (۲۳ با انباشته ۱۰ ← ۳۰).
5. بیشتر از **مقدار حداکثر سفارش** → مقدار **بریده نمی‌شود**؛ ردیف
   «نیازمند بررسی» علامت می‌خورد تا کاربر تصمیم بگیرد.

کنترل حداکثر عمداً در انتها انجام می‌شود تا گرد کردن نتواند بی‌سروصدا از سقف عبور کند.

### قواعد استثنا

نتیجه هر بررسی ساخت‌یافته است (`Proceed` / `Warning` / `RequireReview` / `Skip` / `Error`)
و همراه کد ماشین‌خوان و پیام فارسی بازمی‌گردد — هرگز فقط یک رشته.

| بررسی | کد | نتیجه |
|---|---|---|
| نبود پارامتر سفارش‌دهی | `REPLENISHMENT_PARAMETER_MISSING` | Error |
| پارامتر غیرفعال | `PARAMETER_INACTIVE` | Skip |
| پارامتر منقضی / هنوز نامعتبر | `PARAMETER_EXPIRED` / `PARAMETER_NOT_YET_VALID` | Skip |
| حداکثر موجودی < حداقل موجودی | `INVALID_MIN_MAX_CONFIGURATION` | Error |
| حداکثر سفارش < حداقل سفارش | `INVALID_ORDER_QUANTITY_RANGE` | Error |
| نبود زمان تامین در روش مبتنی بر مصرف | `LEAD_TIME_MISSING` | Error |
| موجودی منفی غیرعادی | `NEGATIVE_ABNORMAL_INVENTORY` | Error |
| نبود انبار / سایت | `WAREHOUSE_MISSING` / `SITE_MISSING` | Error |
| وجود درخواست خرید باز | `OPEN_PURCHASE_REQUEST_EXISTS` | Skip |
| عبور از حداکثر مقدار سفارش | `SUGGESTED_ABOVE_MAXIMUM_ORDER_QUANTITY` | RequireReview |

### جلوگیری از خرید تکراری

کلید کسب‌وکار: **کالا + انبار + سایت**.

وضعیت‌های «باز» که مانع سفارش دوباره می‌شوند:
`Draft`، `Submitted`، `InProgress`، `Approved`.
وضعیت‌های `Rejected`، `Cancelled` و `Closed` مانع نمی‌شوند.

سه لایه محافظت:

1. **هنگام محاسبه** — وجود هر درخواست باز روی کلید کسب‌وکار،
   ردیف را «درخواست باز موجود است» می‌کند و پیشنهادی تولید نمی‌شود.
2. **هنگام ایجاد پیش‌نویس** — ردیف‌های دارای درخواست باز یا پیشنهادهایی
   که پیش‌تر به پیش‌نویس تبدیل شده‌اند، کنار گذاشته و دلیلشان بازگردانده می‌شود.
3. **یکتاسازی عملیات (idempotency)** — فراخوانی `POST /api/purchase-requests/draft`
   با همان `Idempotency-Key` (بدنه یا هدر) همان درخواست قبلی را برمی‌گرداند و
   رکورد تکراری نمی‌سازد. اجرای دوباره اتوماسیون هم درخواست تکراری تولید نمی‌کند.

### آستانه تغییر مقدار

اگر کاربر مقدار درخواست را بیش از **۲۰٪** نسبت به مقدار پیشنهادی تغییر دهد،
ثبت «دلیل تغییر مقدار پیشنهادی» **الزامی** است و در تاریخچه اجرا ثبت می‌شود
(`QUANTITY_CHANGE_REASON_REQUIRED`).

## ۶. مستندات API

پایه: `http://localhost:5220` — مستندات تعاملی در `/swagger`.

### قالب پاسخ

موفق:

```json
{ "success": true, "data": { } }
```

خطا (استثنای خام سرور هرگز بازگردانده نمی‌شود):

```json
{
  "success": false,
  "code": "INVALID_REPLENISHMENT_PARAMETER",
  "message": "حداکثر موجودی نمی‌تواند کمتر از حداقل موجودی باشد.",
  "details": { "maximumStock": "حداکثر موجودی نمی‌تواند کمتر از حداقل موجودی باشد." }
}
```

### پارامترهای سفارش‌دهی

| متد | مسیر | شرح |
|---|---|---|
| `GET` | `/api/inventory-order-parameters` | فهرست (فیلتر: `productId`، `warehouseId`، `siteId`، `isActive`، `search`) |
| `GET` | `/api/inventory-order-parameters/{id}` | خواندن یک پارامتر |
| `POST` | `/api/inventory-order-parameters` | ایجاد |
| `PUT` | `/api/inventory-order-parameters/{id}` | ویرایش |
| `PATCH` | `/api/inventory-order-parameters/{id}/status` | فعال/غیرفعال کردن |

### لیست‌های انتخابی

`GET /api/lookups/{products | warehouses | sites | product-groups | product-natures |
units-of-measure | parameter-scopes | request-types | request-classifications |
quality-control-parameters | test-plans | ordering-methods | comparison-parameters |
recommendation-statuses}`

### محاسبه نیاز سفارش

```http
POST /api/replenishment/calculate
Content-Type: application/json

{
  "fromDate": null,
  "toDate": null,
  "productId": null,
  "warehouseId": null,
  "siteId": null,
  "productGroupId": null,
  "productNatureId": null,
  "parameterScopeId": null,
  "comparisonParameter": null,
  "surplusPercentage": null
}
```

پاسخ شامل `summary` (تعداد بررسی‌شده، پیشنهادها، نیازمند بررسی، کنارگذاشته، خطا)
و `recommendations` است.

### اتوماسیون

| متد | مسیر | شرح |
|---|---|---|
| `GET` | `/api/automation/replenishment/status` | وضعیت، آخرین اجرا، اجرای بعدی |
| `PUT` | `/api/automation/replenishment/settings` | نوع اجرا، ساعت اجرای روزانه، فعال بودن |
| `POST` | `/api/automation/replenishment/run` | اجرای فوری |
| `GET` | `/api/automation/runs?take=50` | فهرست اجراها |
| `GET` | `/api/automation/runs/{id}` | جزئیات اجرا و پیشنهادهای آن |
| `GET` | `/api/automation/runs/{id}/audit` | رویدادهای تاریخچه اجرا |

### درخواست خرید

| متد | مسیر | شرح |
|---|---|---|
| `GET` | `/api/purchase-requests` | فهرست |
| `GET` | `/api/purchase-requests/{id}` | جزئیات |
| `POST` | `/api/purchase-requests/draft` | ایجاد پیش‌نویس (خنثی‌پذیر) |
| `POST` | `/api/purchase-requests/{id}/submit` | ارسال به گردش‌کار |

نمونه ایجاد پیش‌نویس:

```http
POST /api/purchase-requests/draft
Idempotency-Key: 6f1e...c92

{
  "idempotencyKey": "6f1e...c92",
  "automationRunId": 7,
  "lines": [
    { "recommendationId": 12, "requestedQuantity": 650, "quantityChangeReason": null }
  ]
}
```

شماره درخواست به قالب `PR-{سال شمسی}-{۶ رقم}` تولید می‌شود، مثلاً `PR-1405-000123`.

`submit` وضعیت را از «پیش‌نویس» به «ارسال‌شده» می‌برد و
`StartWorkflow(purchaseRequestId)` را شبیه‌سازی می‌کند: یک رکورد
`WorkflowInstance` با شناسه `WF-{شماره درخواست}` ساخته می‌شود.

> در نمونه اولیه احراز هویت پیاده‌سازی نشده است. نام کاربر از هدر
> `X-User-Name` خوانده می‌شود و در نبود آن «کاربر آزمایشی» ثبت می‌شود.

سرویس‌های API (باز کردن پوشش پاسخ، تبدیل خطا، ارسال کلید یکتاسازی)
و رندر نتایج محاسبه در صفحه سفارش‌دهی کالا.

### آزمون دود از انتها تا انتها

با اجرای هم‌زمان بک‌اند و فرانت‌اند:

```bash
cd frontend
node e2e/smoke.mjs
```

کل مسیر را در مرورگر واقعی می‌پیماید و از تصاویر صفحه‌ها عکس می‌گیرد
(`e2e/screenshots/`). با هر خطای کنسول، خروجی ناموفق برمی‌گرداند.

## ۸. مسیر استفاده

1. بک‌اند و فرانت‌اند را اجرا کنید.
2. **پارامترهای سفارش‌دهی کالا** — پارامتر بسازید یا ویرایش/غیرفعال کنید.
3. **سفارش‌دهی کالا** — فیلتر کنید و **«محاسبه نیاز سفارش»** را بزنید.
4. خلاصه و ردیف‌های نتیجه را ببینید؛ در صورت نیاز «مقدار درخواست» را در گرید تغییر دهید.
5. ردیف‌های «نیازمند سفارش» یا «نیازمند بررسی» را انتخاب کنید.
6. **«ارسال درخواست خرید»** → پنجره بازبینی باز می‌شود.
7. **«ایجاد پیش‌نویس درخواست خرید»** → شماره درخواست نمایش داده می‌شود.
8. **«ارسال به گردش‌کار»** → وضعیت به «ارسال‌شده» تغییر می‌کند.
9. **اتوماسیون سفارش‌دهی** → «اجرای الآن» و مشاهده آمار اجرا.
10. **تاریخچه اجرا** → روی یک اجرا کلیک کنید تا ببینید هر کالا چرا پیشنهاد
    گرفته یا کنار گذاشته شده است.
11. اتوماسیون را دوباره اجرا کنید — کالاهایی که درخواست باز دارند
    دیگر پیشنهاد نمی‌گیرند و درخواست تکراری ساخته نمی‌شود.

## ۹. رابط کاربری

- کل چیدمان **راست‌به‌چپ** با برچسب‌های فارسی.
- ظاهر **صفحه عملیاتی ERP**: ناحیه کاری سفید، ورودی‌های فشرده با کادر خاکستری،
  نشانه‌ها و اقدام‌های اصلی نارنجی، گرید متراکم با ردیف فیلتر و صفحه‌بندی.
- مقادیر فنی (شناسه، کد کالا، شماره درخواست، تاریخ و اعداد) در قالب
  چپ‌به‌راست و با فونت تک‌فاصله نمایش داده می‌شوند.
- کامپوننت‌های DevExtreme: `dxDataGrid`، `dxForm`-style layout، `dxSelectBox`،
  `dxDateBox`، `dxNumberBox`، `dxPopup`، `dxTabPanel`، `dxCheckBox`، `dxSwitch`.
- پوسته: `dx.light.compact` به همراه بازنویسی‌های رنگ سازمانی.
- حالت‌های بارگذاری، خالی، خطا، اعلان (toast) و پنجره تایید پیاده‌سازی شده‌اند.

پوسته و ناوبری کامل GNG+ بازسازی نشده است؛ تمرکز روی ناحیه محتوای این صفحات است.

## ۱۰. محدودیت‌های نمونه اولیه

- **احراز هویت و مجوزها** پیاده‌سازی نشده‌اند؛ کاربر از هدر خوانده می‌شود.
- **زمان‌بندی واقعی وجود ندارد.** «زمان‌بندی روزانه» فقط زمان اجرای بعدی را
  محاسبه و نمایش می‌دهد؛ هیچ زمان‌بند پس‌زمینه‌ای اجرا نمی‌شود. اجرا از طریق
  `POST /api/automation/replenishment/run` انجام می‌گیرد.
- **گردش‌کار شبیه‌سازی شده است.** `SimulatedWorkflowService` فقط یک رکورد
  `WorkflowInstance` می‌سازد و به موتور گردش‌کار GNG+ متصل نیست.
- **موجودی از تصویر لحظه‌ای خوانده می‌شود** (`InventorySnapshot`)، نه از
  اسناد انبار به‌صورت زنده.
- **تقویم میلادی** در ورودی‌ها استفاده شده است؛ فقط شماره درخواست خرید
  با سال شمسی تولید می‌شود. برای محصول واقعی به یک تقویم شمسی نیاز است.
- طرح پایگاه داده با `EnsureCreated` ساخته می‌شود؛ **Migration ندارد**.
- تجمیع مقادیر اعشاری در حافظه انجام می‌شود، چون SQLite از `SUM` روی
  `decimal` پشتیبانی نمی‌کند. برای حجم داده واقعی باید به SQL Server منتقل شود.
- صفحه‌بندی و مرتب‌سازی گرید سمت کاربر است؛ برای داده انبوه باید سمت سرور شود.

## ۱۱. پرسش‌های باز

مواردی که در صورت‌مسئله یا تصاویر UI وجود دارند اما رفتار کسب‌وکاری آن‌ها
مشخص نبوده است. طبق خواسته، این فیلدها **در UI و مدل داده حفظ شده‌اند** ولی
رفتار پیچیده‌ای برایشان اختراع نشده است:

1. **ضریب ارزش ویژه** — ذخیره و نمایش داده می‌شود، ولی در هیچ محاسبه‌ای
   وارد نمی‌شود. آیا باید مقدار پیشنهادی یا اولویت سفارش را وزن‌دهی کند؟
2. **تعداد روز برای پوشش حداقل موجودی** و **تعداد روز برای پوشش فروش** —
   ذخیره می‌شوند ولی استفاده نمی‌شوند. احتمالاً باید حداقل موجودی یا سطح
   مطلوب را از روی میانگین مصرف محاسبه کنند. کدام‌یک بر مقدار ثابت اولویت دارد؟
3. **مقدار بهینه سفارش (EOQ)** — در نیازمندی در فهرست نرمال‌سازی آمده ولی
   قاعده‌اش تعریف نشده بود. در اینجا به‌عنوان **کف اقتصادی سفارش** اعمال شده
   است (اگر مقدار پیشنهادی کمتر از EOQ باشد به آن افزایش می‌یابد). اگر
   منظور «مضربی از EOQ» یا «جایگزینی کامل مقدار» بوده، باید اصلاح شود.
4. **پارامتر کنترل کیفیت** و **طرح آزمایش** — ذخیره و در فرم نمایش داده
   می‌شوند ولی بر تولید پیشنهاد اثری ندارند. آیا باید ردیف درخواست خرید را
   برای بازرسی علامت بزنند؟
5. **محدوده پارامتر** — به‌عنوان یک فیلد انتخابی نگهداری می‌شود، ولی سلسله‌مراتب
   واقعی (کالا در انبار ← کالا در سایت ← کالا سراسری) پیاده‌سازی نشده است.
   در حال حاضر پارامترها فقط در سطح «کالا + انبار + سایت» تعریف می‌شوند.
   آیا باید در نبود پارامتر سطح انبار، به پارامتر سطح سایت یا سراسری برگشت داده شود؟
6. **پارامتر مقایسه و درصد مازاد موجودی** — به‌صورت یک فیلتر نمایشی پیاده شده
   است: ردیف‌هایی نگه داشته می‌شوند که موجودی موثرشان از
   `پارامتر مقایسه × (۱ + درصد ÷ ۱۰۰)` بیشتر نباشد. آیا معنای مورد نظر همین است؟
7. **علامت درخواست خرید باز در فرمول موجودی موثر** — طبق صورت‌مسئله،
   مقدار درخواست باز از موجودی موثر **کسر** می‌شود، در حالی که هدف اعلام‌شده
   «جلوگیری از خرید تکراری» است. کسر کردن، موجودی را کمتر و نیاز را بیشتر
   نشان می‌دهد. فرمول **دقیقاً طبق صورت‌مسئله** پیاده شده و جلوگیری از تکرار
   از راه کنترل مستقل «کلید کسب‌وکار» (بند ۱۲ صورت‌مسئله) انجام می‌شود.
   اگر منظور «مقدار در سفارش» به‌عنوان عرضه در راه بوده، علامت باید مثبت شود.
8. **نوع درخواست در سطح پارامتر** — روی پارامتر ذخیره می‌شود ولی هنگام ساخت
   پیش‌نویس، سرآمد درخواست از آن پر نمی‌شود (طبقه‌بندی پیش‌فرض پر می‌شود).
   آیا هر نوع درخواست باید پیش‌نویس جداگانه بسازد؟
